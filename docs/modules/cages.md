# Cages Module

## Purpose

Manages physical shelter cages in the M & P Shelter Monitoring System.

A cage represents a physical housing area used for cats or dogs.

Cage records are preserved because other modules, especially Cage Assignments, Care Records, and Observations, may reference them historically.

Cages are not permanently deleted during normal operations. A cage that is no longer in use can instead be marked as `INACTIVE`.

# Species Group

Allowed values:

- `CAT`
- `DOG`

`MIXED` is intentionally not allowed.

Cats and dogs are not assigned to the same cage because the shelter keeps species physically separated for safety.

The API validator and PostgreSQL CHECK constraint both enforce this rule.

Invalid example:

```json
{
  "speciesGroup": "MIXED",
  "genderGroup": "FEMALE",
  "recommendedCapacity": 4
}
```

Response:

`400 Bad Request`

---

# Gender Group

Allowed values:

- `MALE`
- `FEMALE`
- `MIXED`

`MIXED` here refers only to sex grouping within the same species.

For example:

```text
speciesGroup = CAT
genderGroup = MIXED
```

still represents a cat-only cage.

It does not mean cats and dogs are mixed together.

# Cage Code Generation

Cage codes are automatically generated by the backend.

Examples:

- `CAT-01`
- `CAT-02`
- `DOG-01`
- `DOG-02`

Staff do not manually provide `cageCode`.

CAT and DOG use separate PostgreSQL sequences:

- `cage_cat_code_seq`
- `cage_dog_code_seq`

Conceptual flow:

```text
speciesGroup = CAT
↓
get next CAT sequence number
↓
1
↓
convert to string
↓
pad to two digits
↓
01
↓
CAT-01
```

The service formats the final cage code.

The repository is responsible only for obtaining the next sequence value from PostgreSQL.

---

# Sequence Number Formatting

The service uses:

```js
String(nextNumber).padStart(2, "0")
```

Examples:

```text
1  → 01
7  → 07
10 → 10
```

The final cage code is then created using:

```text
speciesGroup + "-" + paddedNumber
```

Example:

```text
CAT + "-" + 01
↓
CAT-01
```

---

# Cage Code Sequence Gaps

PostgreSQL sequences do not guarantee gapless numbering.

A sequence value may be consumed even when a later operation fails.

This is acceptable because cage codes are identifiers, not accounting numbers.

Normal idempotent request replays are checked before cage-code generation, which prevents unnecessary sequence consumption during ordinary retries.

Rare concurrent races may still consume a sequence value even when one of the resulting INSERT operations is rejected.

---

# Create Cage Idempotency

`POST /api/cages` uses backend idempotency protection.

The purpose is to prevent accidental creation of multiple database cage records for one physical cage.

Without idempotency, a repeated request could create:

```text
first request
→ CAT-01

accidental retry
→ CAT-02
```

Both cage codes would be unique, so `UNIQUE(cage_code)` alone would not detect that the user intended only one physical cage.

Idempotency prevents this duplicate-create scenario.

---

# Idempotency-Key Header

The client sends:

`Idempotency-Key`

as an HTTP request header.

Example:

```text
Idempotency-Key: 6f20a1e4-95ce-4b94-a35d-4c6242f02810
```

The controller reads it using:

```js
req.get("Idempotency-Key")
```

The key must be a valid UUID.

An invalid or missing required idempotency key returns:

`400 Bad Request`

---

# Idempotency Request Hash

After Cage input is validated and normalized, the backend creates a SHA-256 hash representing the intended Cage creation request.

The request hash includes normalized values such as:

- `speciesGroup`
- `genderGroup`
- `recommendedCapacity`
- `cageType`
- `status`
- `location`

Backend-generated values such as:

`cageCode`

are not part of the request hash.

The database stores:

- `idempotency_key`
- `idempotency_request_hash`

---

# Idempotency Database Constraint

The Cages table enforces:

```text
UNIQUE (created_by, idempotency_key)
```

through:

`uq_cages_created_by_idempotency_key`

This prevents one authenticated user from successfully creating multiple Cage records using the same idempotency key.

---

# Idempotency Pre-Check

Before generating a new cage code, the service checks whether the authenticated user has already used the idempotency key.

Conceptual flow:

```text
POST request
↓
validate Idempotency-Key
↓
validate and normalize Cage input
↓
generate request hash
↓
find Cage by createdBy + idempotencyKey
```

If an existing Cage is found:

```text
same key + same request hash
↓
return existing Cage
↓
do not generate another cage code
↓
200 OK
```

If the key exists but the request hash is different:

```text
same key + different request
↓
409 Conflict
```

If no existing request exists:

```text
generate cage code
↓
insert Cage
↓
201 Created
```

---

# Why the Idempotency Check Happens Before Cage Code Generation

Normal retries should not unnecessarily consume another sequence number.

Example:

First request:

```text
generate CAT-01
↓
insert CAT-01
↓
201 Created
```

Exact replay:

```text
find existing idempotency key
↓
same hash
↓
return CAT-01
↓
generateCageCode() is not called
↓
200 OK
```

This keeps ordinary retries from consuming `CAT-02`.

---

# Idempotency Concurrency Protection

The pre-check handles normal sequential retries efficiently.

However, two identical requests may theoretically arrive at nearly the same time:

```text
Request A
→ checks key
→ no row exists

Request B
→ checks key
→ no row exists
```

Both could continue before either INSERT finishes.

Therefore the PostgreSQL UNIQUE constraint remains the final concurrency protection.

PostgreSQL unique-violation error code:

`23505`

is handled when the violated constraint is:

`uq_cages_created_by_idempotency_key`

The service then retrieves the existing Cage and compares request hashes.

Therefore Cage creation uses two layers:

```text
Application pre-check
→ efficient normal replay handling

Database UNIQUE constraint
→ concurrent race-condition protection
```

---

# Idempotency Response Behavior

## New Create Request

New key + new request:

```text
→ create Cage
→ 201 Created
```

## Exact Replay

Same authenticated user  
+ same key  
+ same normalized request

```text
→ return existing Cage
→ no duplicate row
→ normal replay does not consume another sequence number
→ 200 OK
```

## Idempotency Conflict

Same authenticated user  
+ same key  
+ different normalized request

```text
→ reject
→ 409 Conflict
```

Example message:

`Idempotency key has already been used for a different cage request`

A new intended Cage creation must use a new idempotency key.

---

# Why PATCH Does Not Currently Use Idempotency

Idempotency is currently applied to Cage creation but not ordinary Cage PATCH operations.

Example PATCH:

```json
{
  "location": "Cat Area B",
  "recommendedCapacity": 5
}
```

Sending this PATCH twice produces the same main business state:

```text
location = Cat Area B
recommendedCapacity = 5
```

It does not create an additional Cage row.

The `updated_at` audit timestamp may change again, but there is no duplicate physical Cage record.

Idempotency should be reconsidered later for update/action endpoints that produce non-repeatable side effects.

# PATCH Property Detection

PATCH validation needs to determine whether a field was actually included in the incoming request.

The validator uses:

```js
Object.prototype.hasOwnProperty.call(cageData, "location")
```

This distinguishes between:

```json
{}
```

meaning:

```text
do not change location
```

and:

```json
{
  "location": null
}
```

meaning:

```text
intentionally clear location
```

A supplied field can therefore still be meaningful even when its value is falsy, such as:

- `null`
- `false`
- `0`

when those values are valid for that particular field.

# Empty PATCH Protection

An empty PATCH is rejected.

Example:

```json

```

`400 Bad Request`

Message:

`At least one editable cage field is required`

This also protects the repository's dynamic UPDATE query from receiving no editable SQL columns.

# Future Cage Assignment Business Rules

Basic Cage validation checks whether individual field values are valid.

It does not yet decide whether a configuration change is safe for animals currently assigned to the Cage.

For example:

```text
existing Cage = CAT
↓
animals currently assigned
↓
PATCH speciesGroup = DOG
```

`DOG` is individually a valid `speciesGroup`, but changing a currently occupied cat Cage into a dog Cage may be unsafe.

Those database-dependent checks belong in the service/business workflow and will be implemented together with Cage Assignments.

Future rules may include checks before:

- changing `speciesGroup`
- changing `genderGroup`
- reducing recommended capacity
- changing an occupied Cage to `INACTIVE`

This keeps basic input validation separate from database-dependent business logic.

# Dynamic PATCH Repository Pattern

The repository maps API field names to database columns.

Conceptually:

```text
location
→ location

recommendedCapacity
→ recommended_capacity

speciesGroup
→ species_group
```

For this PATCH:

```json
{
  "location": "Cat Area B",
  "recommendedCapacity": 5
}
```

the repository generates the equivalent of:

```sql
UPDATE cages
SET
  location = $1,
  recommended_capacity = $2,
  updated_by = $3,
  updated_at = CURRENT_TIMESTAMP
WHERE cage_id = $4;
```

Only validated fields are added.

```json
{
  "speciesGroup": "MIXED",
  "genderGroup": "FEMALE",
  "recommendedCapacity": 4
}
```

Verified:

`400 Bad Request`

The API rejected the request because Cage species groups are limited to:

- `CAT`
- `DOG`

# Development Decisions and Improvements

## Backend-Generated Cage Codes

Staff do not manually choose Cage identifiers.

Cage codes are generated by the backend from PostgreSQL sequences.

This prevents staff from needing to know which Cage number should be created next.

---

## CAT and DOG Separation

The initial database design allowed:

`MIXED`

for `species_group`.

During implementation, this was removed because cats and dogs should not share the same Cage.

A new migration updated the database instead of editing an already-applied migration.

This preserves migration history.

---

## Gender MIXED Remains Allowed

`gender_group = MIXED` remains valid because it refers to animals of different sexes within the same species.

This is separate from species mixing.

---

## No Hard Delete

No Cage DELETE endpoint was implemented.

Existing cages can instead become:

`INACTIVE`

This preserves future Cage Assignment and care history.

---

## Idempotency Added to Cage Creation

Cage code uniqueness alone does not prevent accidental duplicate physical Cage records because repeated requests generate different valid Cage codes.

Idempotency therefore protects `POST /api/cages`.

---

## PATCH Idempotency Not Added

Ordinary Cage PATCH operations currently modify state rather than create additional records.

Repeating the same PATCH does not create another Cage.

Therefore idempotency is not currently required for normal Cage profile updates.

---

## Future Assignment-Aware Rules

The current Cage module validates Cage configuration independently.

After Cage Assignments are implemented, additional service-level checks can prevent unsafe changes when animals are currently assigned.

Examples include:

- changing CAT Cage to DOG while occupied
- changing gender grouping incompatibly
- setting occupied Cage to INACTIVE
- reducing recommended capacity below current occupancy

These rules belong to the Cage/Cage Assignment workflow rather than basic field validation.
